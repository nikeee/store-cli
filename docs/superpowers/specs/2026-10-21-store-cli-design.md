# store - CLI for App Store Connect and Google Play Console

Status: draft for review, 2026-10-21

## Intent

`store` is a public, open-source command line tool that drives App Store Connect and the Google Play
Console through their official APIs. It replaces clicking through both web consoles and the
hand-rolled release scripts and third-party CI actions that app developers glue together today.

It is used in two places:

- **CI**: non-interactive, credentials from env vars, machine-readable output, waits with timeouts.
- **Locally**: by humans (colored, readable output) and by LLM agents (token-efficient output).

Its second purpose is "store listing as code": the listing (texts, screenshots, review info) lives
as files in the app's repo and is synced declaratively with `push` and `pull`.

The audience is any app developer, not one specific project. The author's app `nikeee/pd` is a
known future user (its `scripts/release/*.ts` and `.github/workflows/CD*.yaml` show a real release
flow), but it will be ported to `store` later and must not shape the design.

## Goals

1. One static binary named `store` for linux/darwin x amd64/arm64.
2. Both stores under one roof, with the same command structure and the same verbs.
3. The whole release cycle without opening a web console: upload a build, distribute it to testers,
   maintain listing texts, screenshots and release notes per locale, add locales, submit for
   review, release and roll out.
4. CI-first: no prompts, env credentials, deterministic exit codes, `--wait` with `--timeout`.
5. Declarative `push`/`pull` of a fastlane-compatible metadata directory.
6. Three output modes: colored text for humans, JSON for scripts, TOON for LLM agents.
7. Strong static typing; API types generated from the official specs; every fact maintained in
   exactly one place.

## Non-goals (v1)

- In-app purchases and subscriptions, pricing and availability, age rating, categories, customer
  reviews, sales/finance/analytics reports, certificates/profiles/devices (signing), Game Center,
  App Clips, custom product pages, product page experiments, Play data safety form.
- Windows builds.
- Building apps (xcodebuild, gradle, EAS), generating screenshots, collecting release notes from
  git or issue trackers.
- Pulling screenshots/images (`pull` handles texts only in v1, see below).
- Config files. Everything is flags plus env vars.
- Interactive login, keychain integration.

Not possible at all through official APIs: App Store privacy labels ("App Privacy"). `store` does
not use web-session or cookie based endpoints.

## Anti-goals (failure even if it technically works)

- Needing Xcode, Ruby, Java, a JVM, or macOS for any command.
- `push` deleting store content that is not represented in the local directory.
- Partial success that exits 0. Every failed API call ends the command with a non-zero exit code
  and the API's own error message.
- Prompts or spinners that hang or garble CI logs.
- Credentials, tokens or auth headers in any output, including `--verbose`.
- The same fact (a field name, a limit, a device size, an env var name) maintained in two places.

## Constraints

- Language: Go (installed: 1.27.3). Module `github.com/nikeee/store-cli`, main package in
  `cmd/store` so `go install github.com/nikeee/store-cli/cmd/store@latest` yields `store`.
- Git remote: `git@github.com:nikeee/store-cli.git`.
- Official APIs only:
  - App Store Connect API, OpenAPI spec 4.5.1, checked in at `api/apple/openapi.oas.json`
    (source: https://developer.apple.com/sample-code/app-store-connect/app-store-connect-openapi-specification.zip).
  - Google Play Developer API (Android Publisher v3), via Google's generated Go client
    `google.golang.org/api/androidpublisher/v3` (generated by Google from the discovery document
    https://androidpublisher.googleapis.com/$discovery/rest?version=v3).
- Credentials only from env vars (names fixed by the user):
  - `APPLE_APPSTORE_ISSUER_ID`, `APPLE_APPSTORE_API_KEY_ID`, `APPLE_APPSTORE_API_PRIVATE_KEY`
  - `GOOGLE_PLAY_SERVICE_ACCOUNT_JSON`
- All user-facing text (help, output, errors, docs) in English.
- Docs and help text use a plain hyphen, never en or em dashes (author's style rule).

## Claude's calls (for the user to check)

1. Go, cobra for the CLI.
2. fastlane-compatible directory layout for `push`/`pull`.
3. `APPLE_APPSTORE_API_PRIVATE_KEY` and `GOOGLE_PLAY_SERVICE_ACCOUNT_JSON` accept either the content
   or a path to a file (content is detected by `-----BEGIN` / a leading `{`).
4. App selection by `--app`, falling back to `APPLE_APPSTORE_BUNDLE_ID` / `GOOGLE_PLAY_PACKAGE_NAME`.
   `store apple build upload` reads the bundle ID from the IPA and needs neither.
5. Google side via Google's official generated client; Apple side via code generated from Apple's
   spec (generator chosen by a spike, see "Code generation").
6. Output mode auto-detection from agent env vars, TOON via `github.com/moonrhythm/toon`.
7. `pull` writes texts only in v1. Apple re-encodes screenshots, so downloaded files never match the
   checksum of the original upload and the next `push` would re-upload every image.
8. In `push`, a present file is the desired value, an empty file clears the field, a missing file
   leaves the store untouched.
9. License MIT. Distribution via GitHub Releases built by goreleaser; Homebrew tap later.
10. Release notes are not part of `push` on Google (they belong to a release, not the listing).

## CLI conventions

- Shape: `store <apple|google> <noun> <verb> [args] [flags]`. Verbs are shared across both sides:
  `list`, `show`, `create`, `set`, `upload`, `delete`, `wait`, `push`, `pull`.
- Global flags: `--output text|json|toon`, `--verbose`, `--dry-run` (mutating commands only),
  `--app`. Apple adds `--platform ios|macos|tvos|visionos` (default `ios`).
- Text values: inline or `@path` to read a file, like curl: `--description @desc.txt`.
- Locales are BCP-47 in App Store style (`de-DE`, `it`, `es-MX`, `zh-Hans`). The Google side
  translates to Play language codes where they differ (`it` -> `it-IT`, `es-MX` -> `es-419`,
  `zh-Hans` -> `zh-CN`), and also accepts Play codes directly. So one release-notes directory can
  serve both stores.
- Builds are referenced by build number (`CFBundleVersion` / `versionCode`) or `latest`. If an Apple
  build number exists for several versions, `--version` disambiguates, otherwise it is an error.
- Long operations take `--wait` and `--timeout <duration>`; polling prints progress to stderr.
- stdout carries only the result; progress and logs go to stderr.
- Exit codes: 0 success, 1 failure (API, validation, timeout), 2 usage error.
- `store completion <shell>` and `store version` come from cobra / ldflags.

## Single source of truth

Each fact below lives in exactly one place; everything else derives from it.

| Fact | Lives in | Derived from it |
|---|---|---|
| API types, enums, endpoints | Apple: generated from `api/apple/openapi.oas.json`. Google: `google.golang.org/api/androidpublisher/v3` | all API calls, enum validation of flags |
| Which Apple operations are used | one codegen config listing operation IDs | the generated client (only those operations) |
| Listing fields | one field table per store: file name, CLI flag, API field, level (Apple: app info vs version), max length | `listing set` flags, `listing show`, `init`, `push`, `pull`, diff, length validation, docs |
| Apple screenshot/preview devices | one device table: display type, CLI alias (`iphone-6.9`), accepted pixel sizes | `--device` validation, size auto-detection in `push`/`upload`, help text |
| Google image types | one table: fastlane dir name, API image type, CLI alias, size limits | `--type`, `push`, help text |
| Locale mapping Apple <-> Play | one table | all Google `--locale` / release-notes handling |
| Env var names | one Go package of constants | auth, help text, README |
| Agent detection env vars | one list | output-mode auto-detection |
| Command reference | cobra command definitions | README command reference and man pages via `cobra/doc`, regenerated by `go generate`; CI fails on drift (`git diff --exit-code`) |
| Version | git tag, injected via ldflags | `store version`, User-Agent |

Limits like Apple's 30/30/100/170/4000 characters or Play's 30/80/4000 are not in the API specs,
so they live in the field table, with the doc URL next to them.

## Code generation

- **Apple:** generate typed Go request/response models and a client from the checked-in spec,
  restricted to the operations the CLI uses. The spec has 1001 paths and is JSON:API-shaped
  (`data`, `attributes`, `relationships`, `included`, `links.next`). The first plan step is a spike
  that tries generators in this order and takes the first that compiles and round-trips real
  responses: `oapi-codegen` v2 with operation filtering, then `ogen`, then a small own generator
  (Go `text/template` over the parsed spec) that only emits what is needed. No known Go client has
  been generated with oapi-codegen or ogen from this spec, so the spike is necessary.
- Generated code is committed, produced by `go generate`, and CI fails on drift.
- Updating the spec is: download the zip, replace `api/apple/openapi.oas.json`, `go generate`,
  fix compile errors.
- **Google:** no own generation; the official client is already generated from the discovery doc
  and supports resumable media uploads.

## Output

- Mode precedence: `--output` flag, then `STORE_OUTPUT` env var (`text|json|toon`), then
  auto-detection: if any agent marker env var is set (`AI_AGENT`, `CLAUDECODE`, plus others the
  builder confirms, e.g. Gemini CLI, Codex, Cursor), the mode is `toon`, otherwise `text`.
- Every command returns one typed result value. Three generic renderers turn it into output; no
  command contains format-specific code. Field names come from the struct's `json` tags, which both
  the JSON and the TOON encoder honor.
- **text**: colored, tables for lists; colors off when stdout is not a TTY or `NO_COLOR` is set.
- **json**: the result value as JSON, stable field names (part of the public interface).
- **toon**: the result value as TOON (spec v3.3) via `github.com/moonrhythm/toon` (encode-only,
  MIT, follows `encoding/json` tags). Fallback if it proves unusable: own encoder, the format is
  small.
- Errors in json/toon mode are rendered in that format on stderr with `error`, `status`, `code`,
  `detail` (from the API), and `hint` (what to do next, where `store` knows it).
- In json/toon mode progress lines on stderr are plain lines, no ANSI.

## Behavior details

### Auth

- Apple: ES256 JWT (`iss` issuer, `kid` key ID, `aud` `appstoreconnect-v1`, max 20 min lifetime),
  cached and renewed before expiry. Team keys only in v1.
- Google: service account JSON, scope `https://www.googleapis.com/auth/androidpublisher`, through
  the official client's credential options.
- `auth check` makes one cheap read call and reports which identity/key is used, never the secret.

### HTTP

- Retries with exponential backoff and `Retry-After` on 429, 5xx and network errors. POST requests
  (creates) are retried only on 429 and connection errors before the request was sent.
- Apple pagination follows `links.next` with `limit=200`.
- `--verbose` logs method, path, status and duration. Never headers or bodies with secrets.

### Apple build upload (no Xcode, no altool, no Transporter)

1. Open the IPA (zip), parse `Payload/*.app/Info.plist` (binary or XML plist): bundle ID,
   `CFBundleShortVersionString`, `CFBundleVersion`. If `--app` is set it must match.
2. Resolve the app ID by bundle ID.
3. `POST /v1/buildUploads` (version, build number, platform) for the app.
4. `POST /v1/buildUploadFiles` (`fileName`, `fileSize`, `uti` `com.apple.ipa`, `assetType` `ASSET`)
   returns upload operations.
5. Upload the parts as the operations describe, a few in parallel, each part retried.
6. `PATCH /v1/buildUploadFiles/{id}` with `uploaded: true` and the MD5 checksum.
7. Poll `GET /v1/buildUploads/{id}` until `COMPLETE` or `FAILED`; print Apple's errors/warnings.
8. With `--wait`: poll the resulting build until processing is `VALID`. With `--notes`: set the
   TestFlight "What to Test" notes as soon as the build exists (no need to wait for processing).
   With `--uses-non-exempt-encryption=false`: set export compliance once the build exists, so it is
   not stuck on "Missing Compliance".
9. Result: app, version, build number, build ID, state.

### Apple `submit` (composite)

1. Find the build (`--build`, default `latest` = newest valid build of that version).
2. Find or create the App Store version for the platform; it must be in an editable state
   (`PREPARE_FOR_SUBMISSION`, `DEVELOPER_REJECTED`, `REJECTED`, `METADATA_REJECTED`,
   `INVALID_BINARY`), otherwise fail with the current state.
3. Attach the build; set release type only if `--release` is given.
4. With `--metadata <dir>`: run `push` against this version.
5. With `--release-notes <dir>`: set "What's New" per locale. Skip with a notice while the app has
   never had a released version (Apple rejects the field then). A locale that has no localization
   on the version is an error that names `push` / `listing locale add`.
6. Submit via review submissions: reuse an open draft (`READY_FOR_REVIEW`) unless it holds a
   different version (then fail), otherwise create one; add the version as item; mark submitted.

### Apple screenshots

- Display type comes from `--device`, from a `<locale>/<device-alias>/` folder in `push`, or from
  the pixel size via the device table (first matching row wins, rows ordered newest first, filtered
  by `--platform`). Unknown size is an error that lists the accepted sizes.
- PNGs with an alpha channel are rejected locally (Apple rejects them after a slow upload).
- Per (locale, display type) the ordered list of local MD5 checksums is compared with the
  `sourceFileChecksum` list of the set. Equal: nothing happens. Different: delete the set's
  screenshots and upload all in order (Apple has no in-place update and keeps upload order).
- Upload: reserve, upload parts, commit with MD5, poll `assetDeliveryState` until `COMPLETE`
  (timeout default 10 min per image; Apple sometimes takes minutes). `FAILED` shows Apple's errors.
- Sets for display types not present locally stay untouched.
- Previews (videos) use the same mechanism but need `--device`; they are not part of `push` in v1.

### Google edits

- Every mutating Google command runs in its own edit: insert, change, commit. On failure the edit is
  deleted. `--changes-not-sent-for-review` is passed to commit where the API needs it.
- `bundle upload`: resumable upload of the AAB, optional deobfuscation file, then one release per
  `--track`. Apps that were never published only accept `--status draft`; the error message must
  say so. The builder verifies against the API docs how existing releases in a track must be carried
  along when setting a new one (especially with staged rollouts).
- `track promote`: takes the named release (or the newest by version code) from `--from` and sets
  it on `--to`, `completed` or `in-progress` with `--rollout`. Release notes for languages the
  listing does not have are dropped with a warning (Play rejects them). Already completed on the
  target: no-op.
- Listing updates merge with the current listing so fields `store` does not manage (e.g. video when
  not given) are kept.
- Images: per (locale, type) compare the ordered list of local SHA-256 with Play's; different means
  delete all of that type and upload in order.

### `push` / `pull`

Directory layout (fastlane-compatible):

```
<dir>/
  <locale>/                       Apple, e.g. de-DE/
    name.txt subtitle.txt privacy_url.txt                      app info level
    description.txt keywords.txt promotional_text.txt
    marketing_url.txt support_url.txt release_notes.txt        version level
  review_information/
    first_name.txt last_name.txt phone_number.txt email_address.txt
    demo_required.txt demo_user.txt demo_password.txt notes.txt
  android/
    <play-language>/              Google, e.g. de-DE/, es-419/
      title.txt short_description.txt full_description.txt video.txt
      images/phoneScreenshots/*.png images/sevenInchScreenshots/*.png
      images/tenInchScreenshots/*.png images/tvScreenshots/*.png images/wearScreenshots/*.png
      images/featureGraphic.png images/icon.png images/promoGraphic.png images/tvBanner.png
<screenshots-dir>/<locale>/*.png  Apple screenshots, default <dir>/../screenshots, flag --screenshots
```

- `store apple push <dir>` reads `<dir>/<locale>/`, `review_information/` and the screenshots dir;
  `store google push <dir>` reads `<dir>/android/`.
- Target Apple version: `--version`, else the one editable version of the platform; none is an
  error that names `version create`. App info fields need an editable app info; if none exists and
  app-info files changed, it is an error (metadata locked in review).
- Local locale missing in the store: localization is created. Store locale missing locally: left
  alone. Removal only via `listing locale remove`.
- `push` first computes a plan (diff local vs. remote), prints it, then applies it; `--dry-run`
  stops after printing. Unchanged fields cause no API call.
- Field lengths are validated before any API call.
- `pull` writes all locales' text files and review information; it overwrites files it writes and
  touches nothing else. No images in v1 (see Claude's call 7).

## Testing

- Unit tests for the pure parts: plist parsing, device detection, field table validation, plan/diff.
- Command tests against `httptest` fake servers. The base URLs of both APIs can be overridden by
  internal env vars for tests only (not documented for users). Tests assert the request sequence
  and the rendered output in all three modes (golden files).
- Fixtures: there are no recorded API responses and no throwaway app to test against (user). The
  fixtures are built from the response fields that the production-proven pd scripts read
  (`../pd/scripts/release/*.ts`), completed from the schemas in the spec. The lessons those
  scripts encode become test cases (see the plan's Review Focus).
- Generated code is not tested directly; drift is caught by `go generate` + `git diff --exit-code`.
- No automated live tests. Read-only commands (`auth check`, `list`, `show`, `pull`) may later be
  smoke-tested by the user against a real app; mutating commands are not tested live.

## Release and CI

- GitHub Actions: `go vet`, `golangci-lint`, tests, `go generate` drift check, on push and PRs.
- Tag `v*`: goreleaser builds linux/darwin x amd64/arm64, archives, checksums, GitHub Release.
- Version from the tag via ldflags.
